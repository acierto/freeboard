# Decisions

Product and implementation decisions, with date and reason (source instruction 5). Sources: `docs/reference/FREEBOARD_SPEC.md` (behavior and safety) and `docs/reference/freeboard-prototype.html` (appearance). Safety invariants win over feature requirements and prototype behavior.

## 2026-11-04 — Foundation

**Core library separated from the Tauri shell.** The Rust crate builds with `--no-default-features` (no Tauri) so guard, runner, store, monitor, scan, detectors and cleanup can be tested on any CI runner without WebKitGTK/WebView2. The `desktop` feature adds `commands/`, `tray.rs` and the shell. Reason: the safety boundary must be testable in isolation, and the core must keep running without a webview.

**`app_core.rs` added to the source layout.** It owns shared state for commands, tray and background tasks. It is named `app_core` rather than `core` to avoid shadowing Rust's `core` crate. Everything else follows the source repository layout.

**Background work uses OS threads, not Tokio tasks.** Monitoring is one sample every five minutes, and scans/cleanups are long-running blocking I/O. Dedicated threads keep the dependency surface small (source instruction 3: avoid dependencies when the standard library is enough); Tauri still uses its own Tokio runtime for IPC.

**The interface never sends paths, including scan folders.** Settings updates from the interface use `UiSettingsPatch`, which has no path fields (`deny_unknown_fields`). Folders are added with `add_folder`, which opens a native picker in the backend; the chosen path never passes through the interface. Removal is by index. Reason: invariant 3 ("The frontend sends only plan and suggestion IDs. It never sends a path"). The dialog plugin is registered in Rust only; the interface has no `dialog:` permission.

**Additional commands beyond the source table.** `get_plan`, `get_run`, `get_trash`, `add_folder`, `remove_folder` and `set_notifications_paused` were added. They take IDs, enums, or numbers only. `get_trash` returns the opaque confirmation token required by `empty_freeboard_trash`.

**IDs are validated before lookup.** Any ID that is not a short token of `[A-Za-z0-9._-]` (no `..`) is rejected with `invalid_id` before reaching the engine (`app_core::validate_id`).

**Protected locations.** The guard rejects (after canonicalizing the parent and never resolving the final component): filesystem roots; home and its ancestors; `Desktop`, `Documents`, `Downloads`, `Library`, `Pictures`, `Music`, `Movies`, `Videos`, `.ssh`, `.config` in home (the folders themselves, not their contents, except `.ssh` which is protected entirely); configured scan folders and the app data directory (themselves); system subtrees (`/System`, `/usr`, `/bin`, `/sbin`, `/etc`, `/Library`, `/Applications`, `/opt`, `/dev`, and on Linux `/lib*`, `/boot`, `/proc`, `/sys`, `/snap`, `/srv`, `/root`, `/var/lib`, `/var/log`; on Windows `Windows`, `Program Files*`, `ProgramData`, `$Recycle.Bin`); `~/Applications`; any `*.app` bundle; any path with a `.git` component; any directory that contains a `.git` entry (repository roots, including linked worktree roots). A tree being deleted that contains a `.git` entry anywhere is refused before anything is removed.

**Commands.** The runner allows only `docker`, `git`, `pnpm`, `pip`, `pip3`, `brew`, `xcrun`, `npm`, `lsof` and `ps`, resolved on `PATH` (plus the standard Homebrew/Docker Desktop locations on macOS, because GUI apps start with a minimal `PATH`). Scans use a read-only subcommand allowlist; cleanups use an action allowlist and require a `Confirmed` token that only the cleanup engine can create. Banned commands (invariant 7) and force flags (except `docker builder prune` / `docker image prune` after confirmation) are refused under both policies. Output is capped at 8 MB; the default timeout is 20 seconds.

**Fake tools in tests use `/bin/sh` scripts.** Production never starts a shell. The test helper `runner::fake::tool` writes executable scripts that stand in for `docker`, `git` and others.

## 2026-11-04 — Monitoring

**Status hysteresis.** Worsening applies immediately. Leaving Critical needs `critical + 2 GB`; leaving Low needs `low + 2 GB`. A jump from Critical straight past `low + 2 GB` goes to Healthy. Threshold changes in Settings apply immediately (hysteresis protects only against noise in measured free space).

**Notifications.** One notification on entering Low from Healthy and one on entering Critical, then a reminder every 6 hours while Critical is unchanged. Improving from Critical to Low does not notify (it is good news, and "Crossing Low or Critical sends exactly one notification" is about getting worse). Paused or disabled notifications are dropped, not replayed. The last status is persisted so a restart does not notify again.

**Pause Notifications** is a toggle that persists until turned off.

**Notification click.** Desktop notification plugins do not report clicks reliably on all platforms. A notification sets a pending view; the next time the app is activated (tray Open, macOS Reopen, or window focus) the shell emits `navigate` to Suggestions. Native click behavior must be checked manually per platform (tasks 2.3).

**Forecast.** Ordinary least squares over the last 14 days of samples (hourly persisted samples plus the current reading). Requires samples spanning at least 3 days. A trend shallower than −0.1 GB/day counts as flat. Cleanup jumps are excluded by removing positive steps that span a Freeboard cleanup or Trash emptying, and any rise of 1 GB or more between consecutive samples (cleanups made outside Freeboard).

**Trend.** One point per day (last sample of each day) for 14 days, plus the current reading, matching the prototype's chart.

**Volumes.** The home volume (longest mount point containing the canonical home path) is always monitored; additional fixed volumes come from Settings. WSL mounts are never included.

## 2026-11-04 — Background lifecycle

Closing the window hides it; a timer destroys the webview after 60 seconds hidden (generation counter cancels the timer when reopened). `RunEvent::ExitRequested` without an exit code is prevented so the app stays in the tray; only the tray's Quit exits. Reopening recreates the webview, which reloads all state from the backend. Login startup is registered only from release builds.

## 2026-11-05 — Docker 29 image listing

Docker 29 leaves untagged images out of a plain `docker image ls`. Freeboard now also runs `docker image ls --filter dangling=true` (read-only, already allowed) and merges the two lists. `--all` is not used because it also lists intermediate build layers, which are not dangling. The test fake behaves like Docker 29 and answers `image inspect` only for the requested IDs, so the test fails without the fix.

## 2026-11-05 — Public preview downloads (requested by the user)

A download page (`site/`, GitHub Pages) and preview installers on GitHub Releases, built by `.github/workflows/release.yml` from a `v*` tag: a universal macOS `.dmg` (ad-hoc signed, not notarized) and Linux `.deb`/AppImage for x86_64 and arm64. Releases are labeled preview and the page explains the macOS "Open Anyway" step. This relaxes the earlier rule that nothing ships before signed artifacts exist; signed, notarized builds remain open (task 5.7). The page uses the prototype-derived fixture screenshots, not captures of a real machine.

## 2026-11-05 — macOS free space excludes purgeable space

The headline free space on macOS is now what the volume has free right now (`statvfs`, the figure `df` shows). It was `sysinfo`'s figure, which on macOS is the important-usage capacity: free plus purgeable space, the figure Finder shows. Purgeable space was then computed as that capacity minus itself, so it was always near zero and never reported, against the platform note "Report APFS purgeable space and local snapshots separately". Found by the user comparing the app (174.4 GB) with `df -h` (116 GiB = 124.6 GB). Thresholds and notifications use the same, more conservative figure.

## 2026-11-05 — Visual verification in CI compares against the prototype rendered on the runner

The stored baselines were rendered on the development Mac (macOS 27). GitHub runners rasterize text differently (about 20,000 differing pixels per capture on Ubuntu, about 1,000 on macOS 15), so the "baseline is still what the prototype renders" check failed for all 199 captures; CI had never run before 2026-11-05, so this had not been seen. CI now runs `verify:visual -- --live` and `verify:visual:selftest -- --live`: the app and the prototype are both rendered on the same runner and compared with the same zero tolerance. The prototype SHA-256 check still applies. The stored baselines are not changed or regenerated in CI; on the machine that made them, `npm run verify:visual` still checks them.

## 2026-11-05 — Findings that were silently missing (found by the user)

- **No project folders, no warning.** Worktrees, project dependencies and build output are found only inside chosen folders ("Scan folders: chosen during first run"). The user skipped onboarding and never saw their two worktrees (7.5 GB). The old note appeared only when Suggestions was empty. Now Suggestions always says when no project folder is chosen, and both Suggestions and the first run offer up to three folders in the home folder that hold Git repositories (read-only listing, two levels deep, no links), each with one click. The interface receives labels and sends back an index, never a path (invariant 3). From Suggestions, adding a folder starts a deep scan.
- **Docker volumes.** Docker labels volumes it creates for containers (`com.docker.volume.anonymous`). Unused ones are now one Risky group ("121 unnamed volumes") with one acknowledgment and one `docker volume rm` of exactly those volumes; every volume is checked again before cleanup and the whole group is skipped if any disappeared or is in use. Named volumes show their Compose project and creation date (`docker volume inspect`, read-only). On the user's Mac this turned about 125 rows into 4.
- **Plan order.** Plans list and clean the biggest items first (stable for equal sizes), so a canceled run has already freed the most.
- **Plan wording.** Only commands use the code font ("Delete the folder" is a sentence). The free-space line no longer reads "now to now + freed": the lower figure is everything except Docker Desktop data, whose virtual disk may not return space right away, and it is one figure when there is none.

These change prototype-derived states; the references carry the same documented edits (`scripts/visual/matrix.mjs`) and the baselines were regenerated with that rationale (entry below).

## Source conflicts

**Repository roots vs. linked worktree removal (task 4.1, decided 2026-11-04 by the user).** The source protects repository roots (invariant 5) but also lists `git worktree remove <path>` for linked worktrees, whose directories are themselves repository roots. Decision: linked worktree roots are the single exception. Only clean Review worktrees (merged, or pushed but not merged) can be removed; removal uses plain `git worktree remove` (never `--force`) after the pre-cleanup probe and `Guard::check_linked_worktree`, which accepts only a non-link directory whose `.git` file points into the main repository's `.git/worktrees/`. The main worktree, `.git` and all other repository roots stay protected. Details and tests: `docs/cleanup.md`.

**npm cache.** `npm cache clean` requires `--force`, which is not an allowed exception, so `cache.npm` removes `_cacache` through the guarded delete path (source detector note).

## 2026-11-04 — Release decisions (task 5.6, decided by the user)

- **License: MIT.** `LICENSE` at the repository root; `license = "MIT"` in `Cargo.toml` and `package.json`; the installers include the license file. Bundled fonts keep their SIL Open Font Licenses (`src/fonts/`).

## 2026-11-04 — Memory target measure (task 5.4, decided by the user)

The 40 MB hidden-in-tray target is measured as the app's own memory as the OS reports it: physical footprint on macOS (`footprint`, Activity Monitor's Memory column), proportional set size (PSS) on Linux, and private working set on Windows. RSS is recorded for reference only, because it counts system-framework pages (WebKit, AppKit) that stay mapped after the webview is destroyed and are shared with other processes. `scripts/perf/measure-process.mjs` reports this measure per platform, and reports "unknown" (never a pass) when it cannot be read.

## 2026-11-05 — Tray mode and single instance (decided by the user for Linux memory)

- **Tray mode (`--tray`).** Freeboard can start with only the tray and monitoring, without creating a window (the configured window is removed before start-up). Login startup uses it on both platforms, so logging in no longer opens a window.
- **Linux: restart into tray mode.** WebKitGTK and its libraries stay resident in a process that has shown a window (measured 100 MB PSS hidden). 60 s after the window is hidden, Freeboard starts `freeboard --tray --after-pid <pid>` and exits; the new copy waits for the old one to exit before starting. It never restarts while a scan or cleanup runs (retries every 30 s). All state it needs is already in SQLite; in-memory five-minute samples of the last day are not carried over (hourly samples are). macOS keeps destroying the webview instead (31 MB footprint already meets the target).
- **Single instance** (`tauri-plugin-single-instance`). A second launch hands over to the running copy, which opens its window. Needed once the app can run with no window: launching it from the app menu must not start a second tray icon.
- **Linux notifications** are shown through the desktop notification service directly (`notify-rust`, already a dependency of the notification plugin) so a click opens Suggestions; the plugin does not report clicks on Linux.

## 2026-11-06 — Rebuild to the new specification (openspec change `rebuild-freeboard`)

**New sources replace the old ones.** The user supplied a new specification and prototype on 2026-11-06. They replace `docs/reference/FREEBOARD_SPEC.md` and `docs/reference/freeboard-prototype.html` in place (hashes in `docs/reference/README.md`); the earlier versions remain in git history. The spec wins on data, safety and behavior; the prototype wins on layout, flows, labels and tone. Reason: the spec's own build-reference rule.

**`build-freeboard` superseded.** The earlier OpenSpec change described the hull-gauge interface. It was deleted (kept in git history) and replaced by `rebuild-freeboard`, chosen by the user. Rust code that meets the new spec is kept and extended; every old screen and flow is replaced (spec: "Do not preserve older screens or flows").

**Unused apps: one narrow exception to protected application directories (decided by the user).** Safety invariant 5 protects application directories, while `apps.unused` moves unused apps to the Trash on macOS. Decision: on macOS only, a single top-level, non-system `.app` bundle directly inside `/Applications` or `~/Applications` may be moved to the Trash — never deleted permanently — and only with its own acknowledgment in the plan. Nothing inside a bundle, no application directory itself and no system app is ever touched. On Windows and Linux the detector links to the system uninstaller. Reason: the spec lists both rules; this keeps the invariant's intent while allowing the listed action.

**Prototype-only parts are not shipped:** example data, Pretend free space, Start over, the forced skip of `old-experiment`, and the simulated Allow access result. The visual verifier hides the first two in the reference.

**Docker disk compaction stays information-only** until a supported method is verified for each platform. Reason: the spec says to show such items for information when no safe, supported action exists.

**Platform scope: Windows is in scope (confirmed by the user, 2026-11-06).** Every milestone must pass on macOS, Linux and Windows, as the new spec requires. This supersedes the 2026-11-04 decision that scoped v1 to macOS and Linux.

**License.** The spec's open question on licensing was already answered: MIT (2026-11-04).

## 2026-11-06 — Home view and tray view (milestone 2)

**The tray view is its own small window.** The prototype simulates the tray with an in-page "Menu bar: 12.4 GB" button and a popover. The app does not show that button: a left click on the native tray icon opens a 312 × 236 window with the popover's content, placed under the icon (or above it when the tray is at the bottom of the screen, as on Windows). It closes with its close button, Esc, or when it loses focus (a click anywhere outside). The menu (Open Freeboard, Scan Now, Pause Notifications, Quit) moves to the right click. Linux desktops do not report tray clicks, so on Linux the menu also has **Show Summary**. The visual verifier hides the in-page button in the reference and compares the tray view on its own. Reason: spec "Background behavior" and "Screen structure" describe a tray view with status, free space, the pile total and a review button.

**The tray window is transparent.** Only the popover card and its shadow show, as in the prototype. On macOS this needs Tauri's `macos-private-api` feature (`app.macOSPrivateApi`); it uses a private AppKit API, which only matters for Mac App Store distribution, a product non-goal. Found on the real menu bar: without it the window showed an opaque square behind the card.

**Linux: WebKitGTK's DMA-BUF renderer is turned off.** On an Ubuntu 24.04 GNOME VM the window stayed blank white: WebKitGTK could not create a GPU buffer screen (`libEGL warning: DRI2: failed to create screen`). Freeboard now sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` at start-up on Linux unless the person set it. The same failure is reported on machines with some NVIDIA drivers. The cost is a slightly slower drawing path, which a mostly static window does not notice.

**Notifications open the home view.** The Suggestions screen no longer exists; a notification click opens the main window on the home view (spec "Disk status").

**Toss and Empty it before cleanup exists.** Until the confirmation sheet (task 5.4) and the Trash confirmation (task 5.5) are built, Toss opens the pile list and Empty it does nothing. The tray view's button opens the main window with the pile shown. *Superseded by slice 2 (2026-11-06): Toss opens the confirmation sheet and Empty it its own confirmation.*

**Commands the Rust core gains later.** The interface already calls `get_pile`, `set_pile_goal`, `set_pile_areas`, `take_out_of_pile` (milestone 4) and `get_disk_map` (milestone 3). Until they exist, the home view shows an empty pile and no coverage badge instead of failing.

**Single text strings.** Labels such as "12.4 GB free" are rendered as one string, as the prototype does. Splitting them into separate React text nodes changes Chromium's text shaping by a few pixels (found by the verifier on the tray view).

## 2026-11-06 — Vertical slices (decided by the user)

**What happened.** Milestone 2 built the new home view against the fixture backend and deleted the old screens. The Rust commands it calls (pile, disk map, Logbook) were planned for milestones 3–5, so the installed app could show free space and the tray view but nothing else: goals did nothing, Where from listed no groups, the pile was always empty, the tabs were empty, scan folders could not be changed, and nothing could be cleaned. The browser checks passed because they run against sample data; the real app was not clicked through.

**Decision.** The remaining work is re-planned as vertical slices (`openspec/changes/rebuild-freeboard/tasks.md`, groups 3–5): find and choose; clean up and Logbook; disk map and the new detectors. Each slice ships its Rust commands and its interface together and ends with a scripted click-through of the real installed app. A contract test makes it impossible for the interface to call a command the Rust core does not have. This departs from the spec's milestone order (read-only product first), but each slice still keeps scans read-only and cleanup behind confirmed plans, so the safety invariants are unchanged. Windows checks wait until after slice 1.

## 2026-11-06 — Slice 1 findings from the real app

- **Old-format results blanked the app.** Builds between migration 3 and the group/parts model kept storing suggestions in the old category model; reading one failed every read, and the window showed only an error. Migration 4 clears them, and unreadable stored rows are now skipped and logged instead of failing the read. Errors show the core's message instead of "[object Object]".
- **No scheduled scan before first-run setup is finished.** A scan reads Downloads, and macOS asked for permission during first run, which the spec forbids. Scheduled scans now wait for setup, even when folders were chosen earlier.
- **Projects are one item split by project.** `node_modules` (and `.venv`, `target`, ...) in several projects become one item with a part per project; each part keeps its own finding, stored in `suggestion_parts`, so slice 2 can clean part by part through the existing checks. Until then the cleanup engine refuses items with parts.
- **Small crates read "<1"**, not "0".
- **Open: deep scans are slow on a real disk.** `~/soft` and `~/proj` (74 repositories) took about 11 minutes, against the spec's 60-second target for a million files. To be profiled in task 5.13.
- **Open: one question per unused Docker image.** A real Docker host gives 246 Quick questions. The spec defines `docker.unused_images` per image; grouping them with parts would follow the spec's "Choose which" pattern. To be decided with the user.

## 2026-11-06 — Fewer, bigger items, and a faster deep scan (decided with the user)

- **One entry per kind, Choose which for the rest.** On a real machine Quick questions listed 397 items. Unused Docker images (244 on that machine) and removable Git worktrees (147) are now one item each, with a part per image or worktree; each part keeps its own finding, so pre-cleanup checks still run per image or worktree. Projects already worked this way. Quick questions went from 397 to 10.
- **Protected items share one card.** The prototype shows one dashed card per blocked item; with 138 blocked worktrees that was a wall. More than one blocked item now shows as "N things I will not touch", with the list folded.
- **Deep scan: one process check instead of one per folder.** Each worktree and project ran `lsof +D <dir>`, which walks the folder's whole tree (20+ s on large worktrees, often timing out and wrongly blocking them as "status unknown"). A scan now reads every process's working folder once (`lsof -d cwd` on macOS, `/proc` on Linux) and matches folders against it; pre-cleanup checks still read fresh. Worktrees are classified and measured in parallel. A deep scan of `~/soft` and `~/proj` (74 repositories, 2.1 M entries) went from about 11 minutes to about 2½. Still above the spec's 60-second target; task 5.13.
- **Scan progress is shown** under the Toss button: files and folders looked through, repositories checked, project folders measured.
- **Folder offers do not look inside Desktop, Documents or Downloads on macOS**, because reading them triggers a permission prompt the person did not ask for. They can still be added with Add folder.
- **Logbook** lists cleanups (the Rust command already existed). The **Disk map** tab says plainly that it is not built yet (slice 3) instead of staying blank.

## 2026-11-06 — Clean up and Logbook (slice 2)

- **Plans cover parts.** A plan item is `{ suggestionId, partIds }`. The parts come from the user's stored Choose which decisions, never from the request (invariant 3). Each selected part runs as its own step, with its own finding, pre-cleanup check and guarded action, so one changed part never stops the others. A split item's combined target is never executed, and a split item whose listed parts lack their own findings is refused. Reason: spec "Item-level controls" and "Pre-cleanup checks".
- **`create_plan` takes `source` and `itemIds`.** `source: "pile"` (with no IDs) plans the pile; `source: "items"` plans the given IDs. Tauri passes command arguments by name, and the contract test allows only typed enums and `*_ids` lists, so the spec's `{ source: "pile" }` or `itemIds` became one enum plus one list.
- **Run records are per part.** The Logbook keeps one record per item or part, linked to its item, and counts crates (plan items) in "Tossed N crates". The progress bar counts crates too, as the prototype does; a crate leaves the boat once any of its parts is removed.
- **A changed part is reported, not the whole item.** The part is skipped with its reason in the result and the Logbook; the item is not marked "Changed, scan again", because its other parts did not change. A changed item without parts keeps the existing mark.
- **After a partial cleanup**, the removed parts leave the item; the rest stay listed with their own sizes, and the item's size and target follow them. The remaining parts are selected again and the item stays out of the pile until a size is chosen again, as in the prototype's `run()`. The item's title keeps the count from the scan ("node_modules in 3 inactive projects") until the next scan; open.
- **The pile resets after every run**, whatever opened it (Toss, Remove now, Remove all here): it keeps its goal and areas and forgets crates chosen by hand, added or taken out. Reason: spec "the pile persists until the next cleanup or reset".
- **Free space is read again when a run ends**, so the status, the tray and the result show the measured change at once instead of after the next five-minute sample. `get_run` also returns the free space measured now, which raises the boat during a run.
- **Expected and measured.** The result shows the measured change. When it differs from what the removed items were expected to free by 0.1 GB or more, a second line gives the expected amount. Skipped and failed items are not counted as expected.
- **Acknowledgment text.** "I understand this cannot be recovered." for unrecoverable items (prototype); "I understand what this removes." for recoverable items that still need their own confirmation (an unused app moved to the Trash).
- **Remove all here** follows the prototype's `usable()`: it excludes blocked, kept, changed and confirmation-needing items, and includes Review items.
- **No usable Trash.** The result says the item was not removed and why, and offers "Delete it permanently instead", which makes a new permanent plan with its own confirmation sheet and acknowledgment. Nothing is deleted as a fallback.
- **Empty it** opens its own sheet ("Empty 2.4 GB from the Trash?"; Recycle Bin on Windows) that says only Freeboard's items are deleted. The confirmation token from `get_trash` binds it to that exact set.
- **Logbook.** Notes use the prototype's sample wording ("Kept 1.2 GB in the Trash", "1 skipped because it changed"). Each row opens run details: every item or part with its action and result, and skipped or failed reasons. Rows are `role="button"` so the list keeps the prototype's markup.
- **Sheets keep focus.** A click on the scrim no longer moves focus out of a sheet. When the control that opened a sheet is gone or disabled after a cleanup, focus goes to "See what is inside".
- **Quirks mode in the reference.** The prototype has no doctype, so the browser renders it in quirks mode, where a small-font second line in a Logbook row is 3 px shorter. The app renders that note as a block, which has the same height in both modes.

## 2026-11-06 — Disk map, blind spots and the disk report (slice 3, tasks 5.9, 5.10, 5.12)

**How the map is built (design D4).** Used bytes are the home volume's total minus free space (on macOS the APFS container's, which is what the volume reports). Bytes are assigned once, most specific first: (1) every suggestion's paths and its parts' paths, nested claims subtracted from the claims around them; (2) area roots measured during deep scans only, each skipping nested roots, claimed paths, exclusions and Docker's virtual disk, with hard-linked files counted once across all roots (`scan::size::account`); (3) on macOS, the other APFS volumes in the container (System, Preboot, VM, Update, and unmounted ones such as Recovery), read with `statvfs`, in the macOS area. Suggestions without paths (Docker images, `brew cleanup`, `pnpm store prune`) are taken to sit inside their area's roots: an area is `path claims + max(roots, tool-level items)`, so they never add on top. Not explained is used bytes minus all of that. Reason: each byte once, without a full disk walk on quick scans.

**Area roots.** Well-known locations in the home folder per platform (caches, AI models, phones and emulators, apps and tools, Docker, Your files; `diskmap/roots.rs`), the scan folders (Projects when they hold repositories, otherwise Your files), every other top-level home folder, and, in the real app only, the system locations outside home on the same volume (macOS: the Data volume's Applications, Library, private, opt, usr and Users/Shared; Linux: `/` on the home device; Windows: the home drive). Other people's home folders are never measured.

**Deep scans only, stored for quick scans.** The measurement is stored (`meta.disk_measurement`) and quick scans reuse it, so a quick scan still never walks the disk (measured: 6.2 s on this Mac, unchanged). Claims that appeared or went since the measurement are reconciled: a path no longer suggested but still on disk goes back into its root; a newly suggested path is moved out of its root. Measured cost of the accounting walk: about 160,000–200,000 entries a second on this Mac's SSD (1,014,001 entries in 5.0–6.4 s, `scan_bench account`). A home with 15 million entries adds about 1½ minutes to a deep scan; to be included in task 5.13's measurements.

**macOS privacy.** Without Full Disk Access Freeboard never reads `~/Library/Containers`, `Group Containers`, `Mail`, `Messages`, `Safari`, `Mobile Documents`, `CloudStorage` or the Photos library, nor Desktop, Documents and Downloads unless they are scan folders, because reading them fails or makes macOS ask the person for something they did not request. They become blind spots: "needs permission" (Allow access) and, for the three personal folders, "a folder I was not asked to scan" with an unknown size. Docker Desktop's `Docker.raw` lives among other apps' data on macOS, so it is read (one `stat`) only with Full Disk Access; without it, the Docker area is the size of Docker's own items. Full Disk Access is checked by opening the system TCC database read-only (no prompt, nothing read).

**Allow access is never simulated.** It opens System Settings > Privacy & Security > Full Disk Access through a new runner policy, `OpenSettings`, which allows exactly one constant command (`open x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles`) and nothing else: no other argument, program or working folder, and `open` stays refused by the scan and cleanup policies (tests in `runner.rs`). The spot stays open; the interface re-checks blind spots when the window regains focus, and once access is granted the spot offers Scan again; it is done only after a deep scan has read the place. Linux and Windows have no such pane: unreadable folders in the person's own folders get Scan again with an explanation, and system folders only the OS can read stay in Not explained (shown as "Space I could not trace to a folder").

**Blind spot rules (design D5).** Unscanned folder: a top-level home folder of 1 GB or more outside the scan folders and exclusions (smaller ones count as Your files). Unknown files: a folder of 1 GB or more directly inside a scan folder that holds repositories, that is not a repository and has no project file; other scan folders are the person's files. Tool unavailable: one spot per tool family from the detector errors. "Scan this folder" adds the folder through the same backend path as Settings and runs a deep scan; "They are mine" writes a `blind_spot_decisions` row and the bytes count under Your files, for good. Resolved spots are shown as done for 7 days, and only after a scan really saw the change.

## 2026-11-07: Worktrees by what can be lost, and their own tab (prototype Version 19)

Found by the user: 140 worktrees were listed as "things I will not touch". The rule blocked every unpushed or unmerged branch, but `git worktree remove` deletes the folder only; the branch and all its commits stay. The prototype Version 19 and spec ("Git worktrees", "Worktrees view") replaced the rule and added a Worktrees tab.

- **Rule (detectors/git.rs):** clean and idle 7+ days → **Ready**: removable, never automatic (Review). The branch is deleted too only when its content is already in the default branch (`git branch -d` when merged, `-D` after the squash check); otherwise it stays, with the `git worktree add` line to reopen it. Used in the last 7 days, or locked → **Needs a look**: selectable by hand, and the plan runs `git worktree unlock` first. Uncommitted or untracked files, a merge in progress, a program using it, commits on no branch, or an unreadable state → **Has your work**: not removed. The main checkout is never an item. Each worktree is now its own item (no grouped item), with its facts in `Suggestion.worktree`.
- **Last use:** the latest of the last commit, the time in the reflog's last entry, HEAD's date, and the folder's date. The reflog *file's* date is not used: `git gc` had rewritten it in every worktree of one repository on the user's Mac, which made 44 idle worktrees look used two days ago.
- **Squash merges are detected read-only:** every file the branch changed since it left the default branch is the same in both (`git diff --quiet <default> HEAD -- <files>`). The spec's `git merge-tree --write-tree` writes objects into the repository, and scans are read-only. If the default branch later changed those files again, the answer is no and the branch is kept: never a wrong yes.
- **Pull requests:** Freeboard does not ask GitHub (`gh pr view`), because it makes no network calls of its own (invariant 12). A merged pull request's content is in main, so the squash check usually finds it.
- **Has your work stays unremovable:** the prototype lets the user tick "I understand these N files will be gone" and then select it. That needs `git worktree remove --force`, which invariant 7 still bans, and the spec's pre-cleanup check still requires no uncommitted files. Not built until the user decides. The reference edit removes the prototype's acknowledgment from captures.
- **Removal:** the normal confirmed plan and run, one worktree at a time. Each Git command has 120 seconds (`WORKTREE_TIMEOUT`), and a timeout fails only that worktree. The run item records "Branch kept." or "Branch deleted too (already in main).", which the Logbook shows. The runner allows `git worktree unlock <path>` and `git branch -d|-D <name>`, and, read-only, `git diff --name-only` and `git diff --quiet`.
- **Interface:** the Worktrees tab (`get_worktrees`) follows the prototype: summary with the rule, a status bar, four status tiles that filter, "Made by agents", a card per repository with "Select N ready", rows that open in place (What I checked, Where, After removal, Would run, Make it removable), and the dock. The main checkout's size is the folder's size at the last measurement less its worktrees. Quick questions, the Disk map's area lists and the places sheet leave worktrees out; Quick questions links to the tab.
- **Supplemental CSS:** three quirks-mode line-height rules (repository heading, repository path, reopen command), and the agent badges darkened for WCAG AA contrast.

## 2026-11-07: Removing a worktree with uncommitted files, after the user's OK

The user agreed: a worktree whose only work is uncommitted files may be removed once the user ticks "I understand these N files will be gone for good" in its row, as the prototype shows.

- **Narrow exception to invariant 7:** `git worktree remove --force` stays banned in the runner's normal checks. Only `Runner::run_acknowledged_removal` accepts it, in exactly `git worktree remove --force <path>`, with an `Acknowledged` token. The cleanup engine creates that token only for an item the confirmed plan recorded as acknowledged (`plan_acks`).
- **Classification:** a merge in progress, a program using the worktree, commits on no branch, or an unreadable state are checked first. Those are never removed, not even with the acknowledgment. Only uncommitted files make an item acknowledgeable (`needs_confirmation`). The branch and its commits stay unless already in main.
- **Pre-cleanup check:** the fingerprint includes the `git status` output, so a file added or changed after the scan skips the worktree ("A new commit or change appeared after the scan.").
- **Interface:** the row's checkbox stays disabled until the acknowledgment is ticked; the plan records each acknowledgment before it runs. The row's "Would run" shows `--force`.

## 2026-11-08: New detectors (tasks 5.1–5.4)

- **One item per kind, a part per thing.** JetBrains versions, closed chat apps, Playwright browsers, Ollama models, Hugging Face repositories and LM Studio models are each one item with Choose which, like projects and worktrees (decision of 2026-11-06). The shared helper `common::split_finding` measures, fingerprints and checks every part on its own.
- **An open Slack, Discord or Teams is its own blocked item**, so the closed ones can still go. Open means a process whose program name contains the app's name (macOS, Linux) or Chromium's `lockfile` in the app's folder (Windows, which has no `ps` here). Unknown blocks.
- **Playwright keeps the newest revision of each browser** besides every revision a project's `playwright-core/browsers.json` asks for, because a Playwright installed outside the scan folders may need it. It runs in deep scans only, since only they know the projects.
- **JetBrains "removed versions"** are versions older than the newest of the same product, judged from cache and settings folders. Only caches (and on macOS logs) are offered; settings never.
- **Docker Desktop's empty space is information only** (spec "If a tool has no safe, supported way..."): no action, no target, shown blocked with the Docker Desktop setting that shrinks it. On macOS it is read only with Full Disk Access, because the disk sits among other apps' data.
- **Ollama "not run for 60 days"** is the newest access or change time of the model's manifest and layers: Ollama records no last-run time, and loading a model reads its layers. Only layers no other model uses are counted. `ollama rm <model>` is allowed with one safe model name per part.
- **Tool output not checked live.** Ollama and LM Studio are not installed on the development Mac, so their formats come from their documented on-disk layouts (manifest v2 JSON, `<publisher>/<model>` folders) and are kept as fixtures. The Hugging Face hub layout was checked against a real cache (2026-11-08): with the newer shared `hub/blobs` folder, a repository's own folder frees little, and the sizes say so. Validate Ollama and LM Studio on a machine that has them before release.
- **"Old" device backups are 180 days without a new backup.** The spec gives no age. A device still in use backs up much more often, so an old backup is usually of a phone or tablet no longer used. It stays Review, because a backup may be the only copy of that device's data. On macOS the backup folder is privacy-protected, so it is read only with Full Disk Access, like Docker's disk.
- **Android emulators**: "not started for 90 days" is the newest change inside the AVD folder, because the emulator writes its disk images while it runs and records no start time. An AVD with `*.lock` files is running and never offered.
- **Unavailable simulators have a part per simulator**, each removed with `xcrun simctl delete <UDID>`, named with the simulator's name and the runtime it needs (from `simctl list devices unavailable --json`, checked live 2026-11-04).
